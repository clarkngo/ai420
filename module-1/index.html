What's the HOS?

HOS 1 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 1, then Analyze and Understand & Refine in Week 2. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 2. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

Most AI apps have a model inside them, and your code decides what happens next. In an agent, the model decides. That difference is the whole course, and this first HOS makes it concrete: first you watch Antigravity, an agent that writes code, plan and carry out a small job in your repo. Then the same five research questions go to a single Gemini call and to an ADK agent you build with Antigravity, and you compare what comes back, including how often the single call confidently guesses.

Week 1 builds the agent and judges it. Week 2 is the harder half: explaining what ADK does event by event, writing a second agentic pattern, plan-and-execute, by hand in ADK, and deciding when a business problem needs an agent at all. Each HOS repo ends as a working agent you can show; together, the four are the start of your portfolio.

Anchoring analogy

A single model call is asking a well-read colleague a question in the hallway: you get an answer from memory, right or wrong, and they walk off. An agent is the same colleague at a desk with a browser and a calculator, allowed to look things up and check their math before answering, and to keep going until they're done. The desk, the browser, and the permission to keep going are what ADK and your tools provide.

Learning objectives

By the end of the two weeks you will be able to:

  1. Distinguish standard LLM inference from an agent, with evidence from your own runs. CO1
  2. Point to where reasoning, planning, tool use, and memory show up in Antigravity and in an ADK agent's events. CO1
  3. Build an ADK agent with function tools and a step budget, and judge what a coding agent built for you. CO2
  4. Compare a tool-calling agent and plan-and-execute on accuracy, steps, tokens, and time. CO1
  5. Decide whether a business workflow needs an agent, a single call, or a fixed script. CO1

Part 1 — Inference vs. an agent ≈ 20 min

Watch first12:28 · IBM Technology

Watch for the shift from a model answering on its own to a system that reasons, acts with tools and keeps going until the task is done. That shift is this whole course. Open on YouTube (human captions).

Inference is one request and one response. The model answers from whatever it learned in training, with no way to check anything. An agent puts the model in a loop: it can ask for an action (a tool call), see the result (an observation), and decide what to do next, until it decides it's done or runs out of steps.

Worked example

"How many years before the first iPhone was the Space Needle completed?" A single call often answers correctly from memory, and sometimes says 47, or confuses the Needle's opening with its design year, with the same confidence. The agent looks up the Space Needle (1962), looks up the iPhone (2007), and calls the calculator: 45. The interesting finding isn't that the agent is right; it's that the single call's right answers and wrong answers look identical.

⚠ Common mistakes

  • Calling anything with a model in it an agent. A chatbot that answers in one call is inference, however clever the prompt. The loop is what makes an agent.
  • Treating a right answer as proof. A single call that's right from memory hasn't checked anything. Ask how the answer was reached.
  • Reaching for an agent first. Agents cost more calls, tokens and time. Many tasks are better as one call or a fixed script (this week's Application Challenge).
Quick check

Name one question a single call can answer reliably and one it can't, and say what the second one needs that the model doesn't have.

Part 2 — The four components, in about 60 lines ≈ 20 min

Watch first2:55 · Google Cloud Tech

This is the mechanism ADK runs for you on every turn. Watch for the moment the model asks for a function instead of answering, and who actually runs it. The model names in the video may be older; use gemini-3.8-flash, as in the hands-on guide. Open on YouTube (human captions).

Go deeper (optional): IBM Technology, What is Tool Calling? (4:56). The same idea without tying it to one vendor.

The course description names four components. In ADK, an agent is a few lines, and you can point at each component in the events it produces:

from google.adk.agents import Agent
from .tools import search_wikipedia, wikipedia_intro, calculate

root_agent = Agent(
    name="research_agent",
    model="gemini-3.8-flash",
    instruction=("Answer multi-step questions. Look facts up with your tools "
                 "and do every calculation with calculate. If no tool "
                 "confirms a fact, say so."),         # steers REASONING
    tools=[search_wikipedia, wikipedia_intro, calculate],   # TOOL USE
)

One question in adk web's Events tab:

user   "How many years before the first iPhone was the Space Needle completed?"
model  function_call      search_wikipedia("Space Needle")   # REASONING: next move
tool   function_response  "...completed in 1962..."          # the OBSERVATION
model  function_call      search_wikipedia("iPhone")
tool   function_response  "...released June 29, 2007..."
model  function_call      calculate("2007 - 1962")
tool   function_response  45
model  text  "The Space Needle was completed 45 years before the first iPhone."

Memory is the session: ADK sends all of these events back to the model on every call, because the model itself remembers nothing. Planning is the one you can't see: here it happens one step at a time, inside each model call. Plan-and-execute (your Week 2 build) makes the plan an explicit, inspectable list. And ADK builds each tool's description from the function's name, type hints and docstring, so those are what the model reads when it chooses.

⚠ Common mistakes

  • A tool with no docstring. The model sees only a name and argument types, so it guesses when to call it. Say what the tool does and when to use it.
  • Running adk web from the wrong folder. Run it from the folder above research_agent/, or the agent list is empty.
  • No step budget. A confused model can call tools again and again, and every call costs tokens. compare.py sets one with RunConfig(max_llm_calls=...).
Quick check

Remove the budget. What's the worst case, and who pays for it?

Part 3 — Agentic patterns and frameworks ≈ 20 min

Watch first8:47 · Google for Developers

The framework you build in all term. Watch for what ADK takes off your hands (the loop, sessions, the web UI) and keep asking: where would I see that step in the Events tab? Open on YouTube (human captions).

Go deeper (optional): Google for Developers, Getting started with Agent Development Kit (18:45): defining an agent, the Runner, and running it locally with adk web.

PatternHow it worksGood forCost
ReActReason, act, observe: one step at a timeOpen-ended lookups where the next step depends on the last resultMany small model calls
Plan-and-executeWrite the whole plan first, then run each stepTasks whose steps are predictable; plans you want to reviewOne planning call + steps
ReflectionReview your own output, then retry or acceptQuality checks (HOS 3)An extra call per review
RoutingClassify the request, send it to a specialistDifferent kinds of requests (HOS 4)A routing call per request

ADK gives you each pattern as a building block. An Agent with tools is a ReAct-style loop. A SequentialAgent runs fixed steps in order, which is how you'll write plan-and-execute in Week 2. A LoopAgent repeats until a check passes (reflection, HOS 3), and a coordinator with sub-agents or a workflow graph routes (HOS 4). Antigravity is an agent too: its /plan is plan-and-execute with you approving the plan. The rule all term: if you can't say which event a pattern produces, you can't debug it.

⚠ Common mistakes

  • Working in Codespaces? Plain adk web returns 403 Forbidden through the forwarded port there. Use adk web --allow_origins "*". On your own computer, plain adk web is fine.
  • Picking a pattern by fashion. Plan-and-execute isn't "more advanced" than ReAct; it suits different tasks. Measure both (Week 2).
Quick check

For "compare three competitors' pricing pages", would you choose ReAct or plan-and-execute? What would change your answer?

▶ Rehearse before the build: Open the Agent Loop Simulator. Run the same question as a single call, as ReAct, and as plan-and-execute; then drop the step budget to 2.

New words this week (6)
Inference
One request to the model, one response back. No actions, no second chances.
Agent
A model in a loop where it can take actions (tool calls), see the results, and decide what to do next until done.
ReAct
Reason + Act: alternating between deciding the next step and taking it. An ADK agent with tools works this way.
Plan-and-execute
Write the full plan first, then work through it step by step.
Event
One recorded step of an ADK run: a user message, a model reply or function call, or a tool result.
Step budget
The most model calls allowed before the run must stop (max_llm_calls in ADK).

    Concept Debate

    Discussion board · 3 stages
    This week's question

    For a multi-step business task, should you build an agent that decides its own steps, or a fixed workflow that calls the model only where needed?

    You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

    How your side is assigned

    Before the first debate you join Debate Group 1 or Debate Group 2, either assigned by your instructor or chosen yourself, as long as the two groups stay close to even. You stay in that group all term; find yours under Communication → Groups. The sides rotate each HOS, so nobody argues the same kind of position all term:

    HOS 1HOS 2HOS 3HOS 4Integration (Wk 8)
    Group 1Side ASide BSide ASide BSide A
    Group 2Side BSide ASide BSide ASide B

    Not in a group? (for example, you added the course late) Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A.

    Side A — Let an agent decide the stepsGroup 1 this HOS

    Give the model tools and a goal; let it choose the path.

    • Real requests vary; a fixed script breaks on the first unexpected case.
    • Adding a capability is adding a tool, not rewriting control flow.
    • The agent can recover from a failed step by trying another route.

    Side B — A fixed workflow with LLM stepsGroup 2 this HOS

    Hard-code the steps; use the model only for the parts that need language.

    • Predictable: the same input takes the same path, so it's testable.
    • Cheaper and faster: no model calls spent deciding what to do.
    • Easier to audit when something goes wrong.
    AI use

    You may use an AI assistant to test your thinking, for example by asking it for the best objection to your side. Your posts must be your own words and your own reasoning: don't paste or lightly edit AI text. If AI changed your thinking, say how in one line. AI Use Guide →
