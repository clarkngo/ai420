Module 1: Anatomy of an Agent

HOS 1Outcome 1

Why before you start: This course's whole idea is the difference between asking a model once and putting it in a loop. If you can point at the loop's parts, every later HOS is "the same loop, plus one more thing."

An agent loop: the model decides, your code acts, the result goes back in.

Inference vs. an agent

Inference is one request and one response: an answer from training data, with no way to check anything. An agent is a model in a loop that can take actions (tool calls), see the results, and decide what to do next.

Why it matters: A single call's right and wrong answers look equally confident; an agent's answer comes with evidence.

The four components

Reasoning — the model's decision at each step. Planning — how it breaks the task down. Tool use — the function calls your code executes. Memory — the session's growing history of events, sent with each call (plus anything saved in state).

Why it matters: Outcome CO1 asks you to point at each one in real code.

The model never runs the tool

It replies with a function call (a name and arguments). ADK runs your Python function and sends the result back as a function response — the observation. In adk web's Events tab, that's one event for the call and one for the response.

Step budget (max_llm_calls)

The most model calls allowed in one run, set with ADK's RunConfig. When it runs out, the agent should say it couldn't finish — not return a half-answer as if it were done.

Why it matters: Without it, a confused agent loops until it runs out of quota.

Agentic patterns

ReAct: one step at a time. Plan-and-execute: a full plan first, then each step. Reflection: review your own output and retry. Routing: send each request to a specialist.

Why it matters: Your ADK agent works ReAct-style in Week 1, and you build plan-and-execute from a SequentialAgent in Week 2; reflection and routing return in HOS 3–4.

When not to use an agent

A fixed workflow is cheaper, faster, and testable. Use an agent when the next step genuinely depends on what the last one returned.

Why it matters: "No agent needed" with a good reason is a strong Application Challenge answer.
Vocabulary check
Observation
what a tool call returned, fed back to the model.
ReAct
Reason + Act, alternating.
Event
one recorded step of an ADK run: a model reply, a tool call, a tool result.
Function response
the message that carries a tool's result back.
Quick self-check before you continue
  • Where does an agent's memory grow during one run?
  • What should happen when the step budget runs out?
  • Name a task where a single call is better than an agent.
Check your thinking
  1. In the session: each model turn and each tool result is added as an event, and ADK sends that history with the next model call. That's why tokens climb as the run goes on.
  2. The loop stops and says honestly that it couldn't finish, with whatever it found. It should not guess, and it should not make one more call.
  3. Anything with one step and no need for outside facts, such as rewriting a paragraph in a friendlier tone. An agent would cost more and add nothing.

Module 2: Custom Tools, MCP & Memory

HOS 2Outcomes 2 & 1

Why before you start: the model never sees your tool's code — only its schema. Writing schemas the model reads correctly, and packaging tools so any agent can use them, is most of HOS 2.

One tool call across the process boundary.

Tool schema

The name, description, and typed parameters the model reads to decide whether and how to call a tool. The description is instructions to the model.

Why it matters: A vague description ("Look up stuff") steals requests from the right tool.

Three kinds of external tools

The course description names APIs, web browsers, and databases. HOS 2 builds one of each: marine weather (Open-Meteo), a page reader (httpx + trafilatura), and read-only SQL against a store database.

Errors as data

A tool returns {"status": "error", "error": "..."} instead of raising. The model can read the error and fix its input; an exception just ends the run.

Why it matters: This is the first self-correction mechanism — HOS 3 builds on it.

MCP (Model Context Protocol)

A standard way to package tools so any compatible agent can discover and call them. Your server runs as a separate process; ADK's McpToolset starts it, asks for its tool list, and forwards calls over stdio.

Why it matters: mcp 2.x uses MCPServer; older tutorials (and many assistants) write FastMCP.

Read-only, twice

The database tool refuses anything but one SELECT and opens SQLite read-only. Either alone can be bypassed by a mistake; together, "cancel order 1003" can't change data.

Short-term vs. long-term memory

Short-term: session state, for this conversation. Long-term: state with the app: or user: prefix, saved by a persistent session service (SQLite here) so it survives a restart. ADK's memory services (load_memory) can also search past sessions. Either way: scoped to the customer, and never secrets.

Why it matters: Unscoped memory leaks one customer's facts to another.
Vocabulary check
stdio
standard input/output — how the agent and the MCP server exchange messages.
Narrow, typed tool
a tool like order_status(order_id: int) instead of free-form SQL.
State prefix
user: or app: on a state key, which decides how widely it's shared and how long it lasts.
Quick self-check before you continue
  • What exactly does the model read when choosing a tool?
  • Why protect the database in two places?
  • What should never go into long-term memory?
Check your thinking
  1. The tool's name, its description, and its parameter types. It never sees your code.
  2. The single-SELECT check can have a gap, and the read-only connection stops a write even if something slips past it. One mistake shouldn't be enough to change data.
  3. Payment details, passwords, and anything you'd be embarrassed to see leaked. Long-term memory is also scoped to the customer, so one person's facts never reach another.

Module 3: Traces & Self-Correction

HOS 3Outcome 3

Why before you start: HOS 3's agent looks fine and fails in five ways — three of them without any error. You'll diagnose them from traces alone, so know what to look for first.

The HOS 3 workflow.

Reasoning trace

The step-by-step record of a run: each model input and output, each tool call with arguments and result, with timing and tokens. In adk web's Trace view, and in the file your HOS 3 recorder writes from ADK callbacks.

Why it matters: In production you usually have the trace, not the code.

Five failure types

Tool-call error (bad arguments crash a tool) · invented action (claims something no tool did) · logic loop (same call, no progress) · wrong data (incomplete results, trusted) · wrong tool (a vague description matched better).

The confident wrong answer

A run that finishes politely and is wrong: nothing in the trace is red. You catch it only by checking each number the agent states against what the tools returned.

Why it matters: It's the most dangerous failure because nobody notices.

Guards as ADK callbacks

on_tool_error_callback turns a raised exception into an error the model can read; a before_tool_callback blocks the same call with the same arguments after two repeats. They don't know about any specific bug.

Why it matters: Guards cure failure shapes (crashes, loops); confident wrong answers need root-cause fixes.

Loop vs. legitimate retry

A retry changes something — the arguments or the approach. A loop repeats without progress. Short cycles (A → B → A → B) slip past a simple identical-call check; a step budget still catches them.

Reflection

A step where the agent reviews its own last result before accepting it, in ADK a LoopAgent with a reviewer that ends the loop when the answer passes. It catches some wrong-data failures, at the cost of extra model calls.

Vocabulary check
Span
one timed step inside a trace.
Root cause
the line of code or instruction that makes the failure happen.
Failure log
scenario, type, first step, symptom, root cause — written before reading the source.
Quick self-check before you continue
  • Why diagnose from the trace before opening the code?
  • Which failure types never crash?
  • What can a guard fix, and what can't it?
Check your thinking
  1. In production you usually have the trace, not the code. Reading the code first also hides how the failure actually shows up.
  2. Invented actions, wrong data and wrong tool. Each ends with a polite reply and no error in the trace. A loop ends without an answer, but it doesn't crash either.
  3. A guard can catch a failure's shape: an exception, a repeated call, too many steps. It can't see that a number is wrong. That takes a root-cause fix, or an evaluation that checks the numbers.

Module 4: Multi-Agent Orchestration & Evaluation

HOS 4Outcome 4

Why before you start: HOS 4 asks whether a team of agents actually beats one agent — and answers with numbers. Know how the numbers are made, and how they can lie, before you trust any.

An evaluation run.

Orchestration

The logic that decides which agent runs when — in sequence, in parallel, in a loop, or by an LLM's choice. ADK's sub_agents lets a coordinator transfer each request to a specialist.

Coordinator + specialists

The coordinator only routes; each specialist (orders, catalog, reports) holds only the tools it needs.

Why it matters: Fewer tools per agent means fewer wrong-tool errors — but every hand-off is another model call.

Agent-on-agent testing

A simulated user plays each scenario's persona toward its goal; a judge grades the transcript against the success rule. In ADK, adk eval runs both: an eval set holds the scenarios, a config file picks the rubric-based criteria. Hundreds of conversations, no person in the loop.

Why it matters: Both are models, so both can be wrong.

Success rate · cost per task · latency

Success rate = scenarios passed ÷ run. Cost per task = (input tokens × input price + output tokens × output price) ÷ scenarios, at list price even on the free tier. Latency per reply as p50 (typical) and p95 (slow case).

Why it matters: Simulator and judge tokens are the cost of testing — count them separately.

Judge agreement

Grade a sample of transcripts yourself and measure how often the judge agrees — and which way it errs (lenient or strict).

Why it matters: An unchecked judge can't support any success-rate claim.

When more agents make it worse

Extra routing calls add cost and latency; two-part questions can get half-answered; a misroute sends a request to an agent without the right tool.

Why it matters: The honest result is often "the team cost more without helping."
Vocabulary check
Transfer
a coordinator handing a conversation to a specialist.
p95
the reply time 95% of replies beat — the slow case users remember.
Shadow cost
what a free-tier run would cost at paid list prices.
Quick self-check before you continue
  • Why count simulator and judge tokens separately?
  • How would you know whether your judge is lenient?
  • Name a request a team handles worse than a single agent.
Check your thinking
  1. They're the cost of testing, not of the agent. Mixing them in makes the agent look more expensive than it is.
  2. Grade some transcripts yourself and compare. Count how often the judge passed something you failed: that's how lenient it is.
  3. A simple single-topic question: the team adds a routing call and can route it wrong, so it's slower and costs more for the same answer.

Putting it together: all 4 HOS

Week 8 reviewTerm ProjectOutcomes 4 & 5

Why before you start: by Week 8 you've built every piece once. The Week 8 architecture review and your Term Project ask a different question: how the pieces connect, and which one catches which problem. Nothing here is new; it's the four modules, joined up.

The path of a customer request

Message → coordinator routes it (HOS 4) → a specialist reasons within its step budget (HOS 1) → a guard checks each tool call (HOS 3) → the tool runs over MCP, and memory is recalled for this customer (HOS 2) → reply. The whole run is one trace, with a span per call (HOS 3).

The path of an evaluation run

Scenario → simulated customer → the agent system, with tokens and seconds recorded → next message or DONE → judge's JSON verdict → success, cost and p50/p95 (HOS 4) → compare with your own labels, the only check on the judge.

Which layer catches what

ProblemWhat catches it
A loop that runs foreverThe step budget (HOS 1), and the repeat-call guard for identical calls (HOS 3)
The model picks the wrong toolA precise description, and narrow typed tools (HOS 2); seen in the trace (HOS 3)
A crafted request tries to change dataThe single-SELECT check and the read-only connection, both (HOS 2)
One customer hears another's factsMemory scoped to the customer (HOS 2)
A tool raises an exceptionThe error guard turns it into an observation (HOS 3)
The agent claims an action it never tookThe instruction and a real tool (HOS 3); a success rule that checks for it (HOS 4)
A confident wrong answerNo guard. Fix the tool that misled it (HOS 3), and catch the rest with an evaluation (HOS 4)
A request sent to the wrong specialistScenarios in the eval, and the trace of the transfer (HOS 3, HOS 4)
A team that only costs moreThe side-by-side report: success, cost per task, p50/p95 (HOS 4)
A judge that's too lenientYour own grading of some transcripts (HOS 4)
Quick self-check before the Week 8 review
  • Can you draw both paths above from memory, labelling each arrow with the HOS it came from?
  • Name one problem no guard can catch, and what catches it instead.
  • Your team's success rate went up 2 points. What else do you need to know before you call that a win?
Check your thinking
  1. If an arrow won't come to mind, reread that HOS's module above. Then step through the same paths in the Week 8 review.
  2. A confident wrong answer. Nothing in the trace is an error, so it takes a root-cause fix or an evaluation that checks the result.
  3. What it cost per task, what happened to p95, how far you trust the judge, and whether 2 points is more than the difference between two runs.
