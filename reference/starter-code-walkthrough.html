How to use this page

Course rules this page follows: everything below runs on your own computer, in Google Antigravity (or in a GitHub Codespace), and needs no credit card. Gemini has a free tier; Google ADK, Open-Meteo, Wikipedia and SQLite need no account.

What "starter code" means in this course

Each HOS has a starter-code template repository on GitHub. You get your own copy by accepting that HOS's invite, linked from its lesson. Unlike a course where one app grows all term, each HOS here starts from its own small project, so you don't carry bugs from one HOS to the next. Your first job in each HOS is reading working code you didn't type. This page explains that code, one HOS at a time.

Don't read ahead. HOS 4's starter contains the repaired agent and the guards you build in HOS 3. Read a section only when you're starting that HOS.

1️⃣

Starting HOS 1

Working tools, an empty agent

The tools, the baseline and the comparison are finished. The ADK agent that uses the tools is yours to build, with Antigravity, and the plan-and-execute version is yours to write by hand.

requirements.txt + .devcontainer/ — setup on your computer, or in a Codespace

On your computer, pip install -r requirements.txt inside your .venv installs everything, including google-adk. The .devcontainer/ folder is only for the Codespaces fallback: there, GitHub builds a Python container, copies .env.example to .env and installs the same requirements for you.

.env.example — where your API key goes 
# Your free Gemini API key — https://aistudio.google.com/apikey
GOOGLE_API_KEY=paste-your-key-here
GOOGLE_GENAI_USE_VERTEXAI=FALSE

A template, safe to commit. Copy it to .env and put your real key there; .env is git-ignored. Treat the key like a password: see the Account & Service Setup Guide.

common.py — shared setup

Loads .env and defines MODEL ("gemini-3.8-flash"), so the model name lives in one place. Everything else imports it from here.

research_agent/tools.py — the three tools

search_wikipedia finds article titles, wikipedia_intro reads an article's introduction, and calculate does arithmetic exactly. They're plain Python functions: ADK builds each tool's description for the model from the function's name, type hints and docstring, so the docstrings matter. Each tool returns a dict, and errors come back as data.

Watch out: Wikipedia blocks requests without a descriptive User-Agent. Keep HEADERS as it is if Antigravity rewrites a tool.
research_agent/agent.py — yours (Create, Part B)

Empty except for a TODO. Your prompt has Antigravity define root_agent here: an ADK Agent with the model, the three tools and an instruction. adk web and compare.py both look for root_agent.

baseline.py — the "before" picture

One request, one response, no tools and no agent. Its run() returns the same dict shape compare.py reads from your agent, so they line up side by side.

tasks.json + compare.py — the test questions and the comparison

Five multi-step questions with expected answers, and a script that runs each through the baseline and your agent (and plan_execute/, once it exists) and prints model calls, tool calls, tokens and seconds, counted from ADK's events. Flags: --verbose, --with-plan, --max-llm-calls (the step budget, through ADK's RunConfig), --only and --pause.

plan_execute/ — yours (Understand & Refine, by hand)

An empty folder for the second pattern: a SequentialAgent of planner, executor and writer that passes the plan along through session state.

Starting HOS 2

A worked example, ready to extend

A store database, an MCP server with one finished tool, and an agent already connected to it. You add the rest.

requirements.txt + .devcontainer/ — setup on your computer, or in a Codespace

On your computer, pip install -r requirements.txt inside your .venv installs everything, including google-adk. The .devcontainer/ folder is only for the Codespaces fallback: there, GitHub builds a Python container, copies .env.example to .env and installs the same requirements for you.

data/seed_db.py — builds harbor.db

Creates Harbor Supply Co.'s SQLite database: customers, products, orders and order items. It's built for you the first time; rebuild it any time with python data/seed_db.py.

mcp_server/server.py — your MCP server

A separate process that serves tools. get_marine_weather is your worked example: it calls Open-Meteo (free, no key), and returns errors as data. New tools follow the same pattern.

Watch out: never print() here. Stdout carries the MCP connection, so use logging. And it's the MCP 2.x import: from mcp.server.mcpserver import MCPServer.
ops_agent/agent.py — the agent

An ADK agent whose only tool is a McpToolset. That toolset starts server.py as a subprocess, asks for its tool list, and forwards calls over stdio. This is also where you add memory: tools that read and write session state with the app: or user: prefix. Started with adk web --session_service_uri "sqlite:///./sessions.db", that state is saved in sessions.db and survives a restart.

Starting HOS 3

A support agent that looks fine

Read this section, but don't open support_agent/tools.py or agent.py until Week 6. You diagnose from traces first, so this section says what the files are for, not what's in them.

requirements.txt + .devcontainer/ — setup on your computer, or in a Codespace

On your computer, pip install -r requirements.txt inside your .venv installs everything, including google-adk. The .devcontainer/ folder is only for the Codespaces fallback: there, GitHub builds a Python container, copies .env.example to .env and installs the same requirements for you.

scenarios.json — six customer messages

Each has an id and a message. There are no expected answers: deciding whether each run succeeded is your job.

run_scenarios.py — runs them and records traces

Runs each scenario through the agent and prints only its final reply, which is why every run looks fine. Flags: --only, --max-calls (the step budget) and --pause. It already imports support_agent/tracing.py if one exists, which is where your trace recorder plugs in: with TRACE=1 set, it saves each trace under traces/.

support_agent/ — the agent under test

An ADK agent and its tools, over the same Harbor Supply database. Leave it closed for Week 5.

Watch out: Antigravity reading these files for you counts as opening them. Tell it not to, and keep it to the recorder task.

Starting HOS 4

The repaired agent, plus test data

The single agent from HOS 3 with its bugs fixed and its guards on, so everyone compares from the same baseline. The team, the eval set, the eval config and the report are yours.

requirements.txt + .devcontainer/ — setup on your computer, or in a Codespace

On your computer, pip install -r requirements.txt inside your .venv installs everything, including google-adk. The .devcontainer/ folder is only for the Codespaces fallback: there, GitHub builds a Python container, copies .env.example to .env and installs the same requirements for you.

single_agent/tools.py + agent.py — the repaired agent

The same support agent, now with a real create_support_ticket, a list_orders that reports its count and combined value, and retail prices only. Your team imports these tools; don't copy them.

single_agent/guards.py — the two guards

error_as_observation turns a tool that raises into an error the model can read. repeat_call_guard blocks the same tool with the same arguments after two calls. Both are generic: they know nothing about any specific bug.

evals/scenarios.json — twelve test scenarios

Each has a persona, a goal and a success rule. You turn them into evals/support.evalset.json for adk eval: the persona and goal become the simulated user's conversation plan, and the success rule becomes what the judge grades against.

evals/pricing.json — the price sheet

Example prices per million tokens. Look up the current list price and replace them before you report cost per task. You pay nothing on the free tier; this is the "shadow cost" of the same run on the paid tier.

▶️

Running it

On your computer (the default): clone your HOS repo and open the folder in Antigravity. In its terminal, once per repo:

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # then put your Gemini key in .env

Then, from the repo's top folder:

# HOS 1
python baseline.py "How many years before the first iPhone was the Space Needle completed?"
python compare.py --verbose

# Any HOS: the ADK developer UI, at http://localhost:8000
adk web

# HOS 2: keep sessions (and memory) across restarts
adk web --session_service_uri "sqlite:///./sessions.db"

# HOS 3: run the scenarios, with your recorder on
TRACE=1 python run_scenarios.py

# HOS 4 (start small: free-tier limits)
adk eval single_agent evals/support.evalset.json:refund-cancelled,order-status --config_file_path evals/test_config.json --print_detailed_results

Open a new terminal later? Run the activate line again first. The full setup, with screenshots of a first run, is in Tools & Setup.

In a Codespace (the fallback): Code → Codespaces → Create codespace on main. The devcontainer installs everything and creates .env; add your key to it. You don't need the .venv there, and you start the developer UI as adk web --allow_origins "*", or it shows a blank page. Stop your Codespace when you're done, because free hours are limited.

🔎

How to read code you didn't write

  1. Start at the entry point. That's compare.py, agent.py or run_scenarios.py, depending on the HOS.
  2. Follow one request end to end. Pick a single question and trace it file by file before you read anything else.
  3. Run it before you change it. Ask something it can answer, then something it can't. Watching real behavior beats guessing.
  4. Break it on purpose. Blank the API key, send a bad argument, ask for something no tool can do. Knowing how it fails is how you know you understand it.

This is the same habit the Evaluate and Analyze stages of every HOS are training.
