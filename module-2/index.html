What's the HOS?

HOS 2 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 3, then Analyze and Understand & Refine in Week 4. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 4. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

The course description names three kinds of external tools: APIs, web browsers, and databases. In this HOS you build one of each for Harbor Supply Co., a marine supply store near Seattle, and serve them from your own small MCP server that a Google ADK operations agent connects to.

The second half adds memory: short-term (who you're talking to, this session) and long-term (a customer's preferences, recalled days later). Week 4 asks why the model picked the tool it picked, and makes that choice safer with narrow, typed tools you write by hand.

Anchoring analogy

Tools are the agent's hands, and their schemas are the labels on the drawers. The model never sees your code, only the label: name, description, and parameter types. A drawer labeled "stuff" gets opened for everything. Memory is the difference between a store clerk with a notepad (this conversation) and one with a customer file (every conversation).

Learning objectives

By the end of the two weeks you will be able to:

  1. Implement custom API, browser, and database tools and integrate them into an agentic loop via function calling. CO2
  2. Write tool schemas precise enough that the model picks the right tool with the right arguments. CO2
  3. Protect a database tool so the agent can't change data, even with crafted SQL. CO2
  4. Serve tools over MCP and explain what crosses the process boundary. CO2
  5. Distinguish short-term from long-term memory, and decide what should never be stored. CO1

Lecture: tools, schemas, and memory

≈ 50 min with videos3 short partsCO1 · CO2

Three short segments instead of one long one: watch the video, read the notes, then try the quick check before moving on. The notes cover everything you need, so the videos are a second explanation rather than a requirement. If something stays fuzzy, that's exactly what your Muddiest Point is for.

Part 1 — A tool is a schema the model reads ≈ 15 min

Watch first4:56 · IBM Technology

Watch for what the model is given about each tool, and what it sends back when it wants one. That description is the whole interface this part is about. Open on YouTube (human captions).

When a model decides to call a tool, it's reading three things: the name, the description, and the parameter types. That's the whole interface. The description is instructions to the model, and it matters as much as the code behind it.

@server.tool()
def query_database(sql: str) -> dict:
    """Run one read-only SQL SELECT against the Harbor Supply Co. database.
    Tables: customers(id, name, email, city), products(...), orders(...)
    Returns at most 50 rows; `truncated` is true if there were more."""

Two rules carry through the whole course: tools return errors as data ({"status": "error", ...}) so the model can read them and adjust, and tools that can change the world get the narrowest possible interface.

⚠ Common mistakes

  • A description that says what the code does, not when to use it. "Runs SQL" doesn't tell the model when this tool is the right one. Say which questions it answers.
  • Loose parameter types. q: str invites the model to guess the format, differently each time.
  • Raising instead of returning an error. The run crashes, and the model never gets to say "I couldn't find that order".
Quick check

If the docstring didn't list the tables, what would the model do when asked "how many orders are backordered?"

Part 2 — APIs, browsers, databases — and MCP ≈ 20 min

Watch first3:46 · IBM Technology

Watch for the three parts of MCP (host, client, server) and match them to your build: ADK is the host, McpToolset is the client, and mcp_server/server.py is the server. Open on YouTube (human captions).

Go deeper (optional): IBM Technology, MCP vs API: Simplifying AI Agent Integration with External Data (13:10).

API: get_marine_weather calls Open-Meteo (free, no key) — the worked example. Browser: fetch a page, strip menus and ads, return clean text with a length limit so one page can't flood the context. Database: read-only SQL, protected twice — a single-SELECT check and the database opened read-only, so even a clever query can't write.

MCP (Model Context Protocol) packages tools so any compatible agent can discover and call them. Your server runs as a separate process; ADK's McpToolset starts it, asks for its tool list (names, descriptions, schemas), and forwards calls over stdio.

Worked example

"Cancel order 1003." With only a free-form SQL tool opened read-write, a helpful model writes an UPDATE. With the double protection, the SELECT check refuses it, and even if it slipped through, SQLite in read-only mode would too. The agent tells the customer it can't cancel orders, which is the correct outcome.

⚠ Common mistakes

  • print() in the MCP server. Anything written to stdout corrupts the MCP connection. Use logging, which writes to stderr.
  • The 1.x import. On MCP 2.x, FastMCP became MCPServer (from mcp.server.mcpserver import MCPServer). Many tutorials and assistants still write the old one.
  • Silent truncation. A browser tool that cuts a page without saying so leads to confident answers about text the model never saw.
Quick check

The MCP server crashes in the middle of a conversation. What does the agent see, and what should it tell the customer?

Part 3 — Memory: this conversation vs. every conversation ≈ 15 min

Short-term memory is ADK session state: a tool writes tool_context.state["current_customer"] = "Ana Reyes", and it lasts until the session ends. Long-term memory has to outlive the session. ADK state keys with the app: prefix are shared by every session of the app, and user: keys by every session of one user. Start adk web with a database behind it and they survive a restart too:

adk web --session_service_uri "sqlite:///./sessions.db"

# in a tool: one place for every customer's lasting facts
facts = dict(tool_context.state.get("app:customer_facts", {}))
facts.setdefault("Ana Reyes", []).append("prefers email updates")
tool_context.state["app:customer_facts"] = facts   # assign it back to save it

ADK also has memory services that search past conversations by meaning, through its load_memory tool. In adk web the default one lives in memory and is lost on restart; Google Cloud's Memory Bank is the hosted version (optional, not needed for this course). The idea is the same: the agent looks things up instead of remembering them.

Long-term memory is also a liability. Scope it to the customer (Ana's facts never surface for Marcus): with app: state, that scoping is your tool's job, not ADK's. And decide what must never be stored: payment details, passwords, anything you'd be embarrassed to see leaked.

⚠ Common mistakes

  • Editing the dict in place. state["app:customer_facts"]["Ana"] = ... isn't saved. Change a copy and assign it back, as above.
  • Storing everything. A long-term store full of chit-chat makes recall worse, not better. Save lasting, useful facts only.
  • Unscoped recall. Returning every customer's facts lets the model mention someone else's.
  • Forgetting the database flag. Without --session_service_uri, adk web keeps sessions in memory, and "long-term" memory disappears on restart.
Quick check

Name one fact about a customer that belongs in long-term memory, and one that must never go there. What makes the difference?

▶ Rehearse before the build: Open the Tool Schemas & MCP Simulator. Make a tool description vague and watch tool choice degrade; then attack the database tool with each protection turned off.

New words this week (5)
Tool schema
The name, description, and parameter types the model reads to decide whether and how to call a tool.
MCP (Model Context Protocol)
A standard way to package tools so any compatible agent can discover and call them.
Read-only protection
Refusing writes in the tool's own check and in how the database is opened, so one mistake isn't enough.
Short-term vs. long-term memory
What the agent holds during one conversation, versus what it stores to recall in a future one.
State prefix
How ADK scopes a state key: none (this session), user: (every session of one user), app: (every session of the app), temp: (this turn only).

    Concept Debate

    Discussion board · 3 stages

    Should an agent get one flexible, general tool (like free-form SQL) or many narrow, typed tools?

    You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

    How your side is assigned

    Before the first debate you join Debate Group 1 or Debate Group 2, either assigned by your instructor or chosen yourself, as long as the two groups stay close to even. You stay in that group all term; find yours under Communication → Groups. The sides rotate each HOS, so nobody argues the same kind of position all term:

    Side A — One flexible toolGroup 2 this HOS

    Give the model free-form SQL (read-only) and let it write the query it needs.

    • Covers questions nobody anticipated.
    • One tool to describe, maintain, and secure.
    • Models are good at SQL; typed tools limit them.

    Side B — Many narrow toolsGroup 1 this HOS

    Give the model order_status(order_id), low_stock_report(), and similar.

    • Typed parameters make wrong calls harder.
    • Each tool's output is predictable and tested.
    • Narrow tools are safer to expose to customers.
