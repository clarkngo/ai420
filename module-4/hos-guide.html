HOS 4: Multi-Agent Orchestration & Evaluation

Turn Harbor Supply Co.'s single support agent into a team — a coordinator plus specialists — and then find out, with numbers, whether the team is actually better. Test both versions the way industry does: a simulated customer talks to each one, a judge agent grades every conversation, and you report success rate, cost per task, and latency.

Before you start

  1. Check your account setup. Nothing new: your GitHub account and Gemini API key. Your HOS 3 trace recorder is optional here.
  2. Know the concepts. Read Concept Companion → Module 4 before you open the starter code.

What you'll need

  • Starter code: your HOS 4 repo, created when you accept the HOS 4 invite. Clone it, open the folder in Antigravity, make the .venv and run pip install -r requirements.txt (or open it in a Codespace, where that happens for you). Not sure what a file does? See the starter code walkthrough for this HOS.
  • Your free Gemini API key (no credit card) from aistudio.google.com/apikey. In the HOS folder: cp .env.example .env, then paste it in as GOOGLE_API_KEY.
  • Google Antigravity, the free desktop app, for Stage 1 (install guide). In a Codespace, use Copilot instead.

Reference reading (optional, before you start)

  • Google ADK documentation: the pages on multi-agent systems (sub_agents and transfer), workflow agents (sequential, parallel, loop, and graph workflows), and evaluation (adk eval, eval sets, criteria and user simulation).

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your Module 4 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go, then submit the repo link to the HOS 4 assignment in Brightspace by the end of Week 8.

🛠️

1 · Create / Scaffold

Graded as Engagement: 20% of this HOS. The AI-assisted starting point, not the deliverable.

The starter gives you the repaired single agent from HOS 3 (single_agent/), twelve test scenarios (evals/scenarios.json: a persona, a goal, and a success rule each), and a price sheet (evals/pricing.json). There's no prompt this time. Here's the goal. You decide the design and direct Antigravity; start with /plan and read the plan before you approve it:

  1. A team version in team_agent/: a coordinator with no tools whose sub_agents are the specialists, each specialist holding only the tools it needs. Reuse single_agent/tools.py and guards.py; don't copy them. Try it in adk web and watch the transfer in the Events tab.
  2. An eval set (evals/support.evalset.json): each scenario as a conversation scenario for ADK's simulated user, with a starting prompt and a conversation plan built from the persona and goal. The plan says when the customer is done.
  3. Judge and metric settings (evals/test_config.json): a rubric-based criterion, so an LLM judge grades each conversation against that scenario's success rule, plus ADK's efficiency criteria for tokens, model calls and time. Then run both systems: 
    adk eval single_agent evals/support.evalset.json --config_file_path evals/test_config.json --print_detailed_results
adk eval team_agent evals/support.evalset.json --config_file_path evals/test_config.json --print_detailed_results
  4. A report (evals/report.py) that reads the results adk eval saved, writes evals/results/<system>.json (one row per scenario: the conversation, the verdict and its reason, tokens, seconds), and prints, side by side: success rate; cost per task (input and output tokens × the prices in pricing.json); and latency per agent reply, as p50 and p95. These numbers cover the agent only; the simulated user and the judge are the cost of testing.

Free-tier budget: a full run is roughly 10–15 model calls per scenario, so all twelve scenarios on both systems is about 250–350 calls. Get it working with 2–3 scenarios first: add their ids after the eval set's file name, as in evals/support.evalset.json:refund-cancelled,order-status. Consider a smaller model for the simulated user and the judge; the config file sets both.

Submit (Engagement)
  • The prompts you gave Antigravity and a two-line summary of its plan, and a screenshot of a team run in adk web showing a transfer to a specialist.
🔍

2 · Evaluate

The critical gate — is the AI-produced result actually correct?

Before you trust any number, check the harness itself:

  • Read three simulated conversations end to end (--print_detailed_results prints them). Does the simulated customer stay in character and stop when its goal is met, or wander off and pad the conversation?
  • Check the metric math by hand for one scenario: tokens × price = the cost it reported? Is p95 really the 95th percentile of the reply times, or something else?
  • Find a scenario where the judge's verdict looks wrong to you, if there is one. What in the success rule or the rubric let it happen?
Submit
  • Your side-by-side report (all three metrics for both systems).
  • A short note on what you checked in the harness, and anything you had to fix before trusting the numbers.
🔬

3 · Analyze

Why do the numbers come out the way they do?

Explain your results. Did the team beat the single agent on success rate? Whatever the answer, it probably cost more tokens and time. Using one or two specific traces, explain where the extra cost comes from (hint: count the model calls the coordinator adds on each turn), and name one kind of request where splitting into specialists helps and one where it only adds overhead.

Submit
  • A short written analysis, in your own words, citing at least one specific conversation.
✋

4 · Understand & Refine

The mastery check — by hand, no AI assistance for this stage.

By hand this time — no AI assistance for this stage.

An LLM judge is only worth trusting as far as it agrees with careful human grading. Measure that yourself:

  • Read at least six transcripts from one run and record your own pass/fail in evals/human_labels.json (e.g. {"vhf-price": true, "refund-cancelled": false}).
  • Write evals/agreement.py: it compares your labels with the judge's verdicts in evals/results/ and prints the agreement rate, which scenarios the judge passed that you failed (too lenient), and which it failed that you passed (too strict), with the judge's stated reason for each.
Submit
  • Your agreement.py and human_labels.json.
  • The agreement rate, and two or three sentences: would you report this judge's success rate to a manager as-is? If not, what would you change first?
🧯

Common snags

  • The coordinator answers questions itself instead of transferring — its instruction has to say plainly that it doesn't answer, only routes, and each specialist's description has to make ownership obvious. The coordinator reads those descriptions to decide where to send a request.
  • A two-part question only gets half answered — after transferring, the specialist owns the conversation. Tell specialists to transfer back to the coordinator when the rest of the request isn't theirs.
  • The simulated customer never stops — its conversation plan has to say when it's done, and the simulator needs a turn limit (check the ADK eval docs for the setting in your version). Without one, one confused conversation can use up your free-tier quota.
  • A criterion errors or scores nothing — criteria that compare against an expected tool trajectory or an expected reply need a fixed, scripted conversation. A simulated user never follows a script, so use rubric-based criteria with it.
  • report.py can't find the results — print where adk eval saved them on your machine (the path is in its output or in the ADK docs) rather than guessing.
  • Your costs look impossibly low — pricing.json ships with example prices. Look up your model's current list price and update it before you report cost per task.
  • 429 RESOURCE_EXHAUSTED — you hit the free tier's per-minute limit. Wait a minute and rerun; or run fewer scenarios at a time.
  • In a Codespace only: adk web opens a blank page, and the terminal shows 403 Forbidden for /dev-ui/...js files — ADK blocks requests that arrive through Codespaces' forwarded URL. Stop it and start it as adk web --allow_origins "*", then hard-refresh the tab. That's safe here: Codespace ports are private to your GitHub account by default.
  • 502 Bad Gateway, a 404 or "model not found" — almost always the model name. Coding agents, Antigravity included, default to whatever model was current in their training data, such as gemini-2.5-flash, which new API keys can't use. Set it back to gemini-3.8-flash. If that ever stops working, check the current list at ai.google.dev/gemini-api/docs/models.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 4.
