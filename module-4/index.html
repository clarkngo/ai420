What's the HOS?

HOS 4 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 7, then Analyze and Understand & Refine in Week 8. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 8. The Muddiest Point, Concept Debates, Application Challenge and Knowledge Check are graded separately.

Multi-agent systems are easy to build and easy to oversell. This HOS does both halves honestly. First, a coordinator that routes each request to an orders, catalog or reports specialist, each holding only its own tools. Second, an evaluation harness where a simulated customer talks to each system across 12 scenarios while a judge grades the transcripts.

The deliverable is a comparison, not a winner: success rate, cost per task, and p50/p95 latency for the single agent and the team. Week 8 checks the judge against your own grading, then steps back to connect all four HOS in an architecture review and the Integration Concept Debate.

Anchoring analogy

A coordinator with specialists is a hospital front desk: triage sends you to cardiology or orthopedics, and each specialist has their own tools. It works better, until the front desk adds a wait to every visit or sends you to the wrong floor. Agent-on-agent testing is the mystery shopper: hundreds of fake patients with scripted complaints, and an auditor who reads every visit note. You only trust the auditor after checking a few notes yourself.

Learning objectives

By the end of the two weeks you will be able to:

  1. Build a coordinator that delegates to specialist agents, each with only the tools it needs. CO4
  2. Build an agent-on-agent harness: simulated user → agent system → judge → metrics. CO4
  3. Measure success rate, cost per task (tokens × price), and p50/p95 latency. CO4
  4. Check an LLM judge against human grading, and say which way it errs. CO4
  5. Explain, with traces, where a multi-agent system's extra cost comes from. CO4

Lecture: orchestration and evaluation

≈ 60 min with videos3 short partsCO4

Three short segments instead of one long one: watch the video, read the notes, then try the quick check before moving on. The notes cover everything you need, so the videos are a second explanation rather than a requirement. If something stays fuzzy, that's exactly what your Muddiest Point is for.

Part 1 — Orchestration: who runs when ≈ 20 min

Watch first6:41 · IBM Technology

Watch for what the orchestrator does itself and what it hands off. In this HOS the coordinator does nothing but route. Open on YouTube (human captions).

Go deeper (optional): IBM Technology, Multi AI Agent Systems (10:55).

Orchestration is the logic that decides which agent runs next: in sequence, in parallel, in a loop, or by an LLM choosing (ADK's sub_agents with transfer_to_agent). In this HOS the coordinator never answers questions itself. It reads the request and transfers to the specialist that owns that kind of question. When the order of steps is fixed, a workflow agent (SequentialAgent, ParallelAgent, or an ADK 2.x Workflow graph) does the routing in code, with no model call to decide.

AgentToolsOwns
coordinatornoneRouting only
orders_agentget_order, check_shipment, create_support_ticketA customer's own orders, shipping, refunds (by ticket)
catalog_agentsearch_products, get_productProducts and retail prices
reports_agentlist_ordersStore-wide numbers, for staff

⚠ Common mistakes

  • Copying the tools into the team. Import single_agent/tools.py and guards.py; two copies drift apart and your comparison stops being fair.
  • A coordinator that answers. If it can answer, it will, and routing becomes guesswork.
  • Splitting by topic when tool access is the real line. Staff-only tools are the strongest reason to split.
Quick check

Count the model calls for "where is order 1004?" in the single agent vs. the team. Where do the extra ones come from?

Part 2 — Agent-on-agent testing ≈ 20 min

Watch first6:08 · IBM Technology

Watch for the ways a judge goes wrong, then look for each one in your own judge's verdicts. Open on YouTube (human captions).

Nobody hand-tests 12 scenarios × 2 systems × every change. Instead, a simulated user (an LLM playing a customer with a goal) holds a multi-turn conversation with the system under test. Then a judge (an LLM) grades the conversation against a written rubric: what must happen and what must not. ADK does both with adk eval: an eval set holds the scenarios, and a config file picks the criteria. Each scenario looks roughly like this (check the ADK eval docs for the exact fields in your version):

{"eval_id": "refund-cancelled",
 "conversation_scenario": {
   "starting_prompt": "Hi, I need a refund for order 1005.",
   "conversation_plan": "You are Tom Okafor, polite but in a hurry. You want
     a refund for cancelled order 1005. Once the agent opens a ticket
     or says it can't help, end the conversation."}}

Rubric for the judge: the agent confirms 1005 is cancelled and opens
a ticket. It does NOT claim the refund was issued.

Both roles are models, so both can be wrong. The simulated user can wander off its goal or never stop; the judge can be too lenient or too strict. That's why Week 8 ends with agreement.py: how often does the judge agree with you?

⚠ Common mistakes

  • A vague success rule. "The agent is helpful" lets the judge pass almost anything. Say what must happen and what must not.
  • A simulated user with no way to stop. Say in the plan when the customer is done, and set a turn limit, or it pads every run.
  • Criteria that need a script. Exact-match criteria (the expected tool calls or reply) compare against a fixed conversation, and a simulated user never follows one. Use rubric-based criteria with simulated users.
Quick check

The judge passes a transcript where the agent said "your refund has been issued." Which part of the scenario above should have failed it?

Part 3 — Three numbers: success, cost, latency ≈ 20 min

Success rate = scenarios the judge passed ÷ scenarios run. Cost per task = (input tokens × input price + output tokens × output price) ÷ scenarios, computed at list price even on the free tier: the "shadow cost" of a paid deployment. Latency per agent reply, reported as p50 (typical) and p95 (the slow case users remember).

ADK's efficiency criteria report each run's tokens, model calls and time; your report.py turns them into the three numbers. Those numbers cover the agent. The simulated user and the judge cost extra: that's the cost of testing, not of the agent, so don't mix them in.

Mind the free tier

A full run is roughly 10–15 model calls per scenario, so 12 scenarios on both systems is a few hundred calls. Start with 2–3 scenarios until it works (adk eval can run only the cases you name), and consider a smaller model for the simulated user and the judge.

Quick check

The team's success rate is 2 points higher and its cost per task is 40% higher. What would you need to know before recommending it?

▶ Rehearse before the build: Open the Multi-Agent Eval Lab. Make the coordinator's routing worse, make the judge lenient, and watch the success rate you'd report drift away from the true one.

    Side A — One capable agentGroup 2 this HOS

    Keep a single agent with all the tools and a good instruction.

    • Fewer model calls per request: cheaper and faster.
    • No routing mistakes, because there's nowhere to route wrong.
    • Simpler traces to debug.

    Side B — Coordinator + specialistsGroup 1 this HOS

    Route each request to a specialist holding only its own tools.

    • Each specialist has a short instruction and few tools, so fewer wrong-tool errors.
    • Staff-only tools (store-wide reports) stay away from customer-facing agents.
    • Specialists can be tested and improved separately.

    Application Challenge — test a vendor's "94% success rate"

    Build to spec · 60–90 min

    A vendor is selling Cascade Accounting Services a team of agents that reads supplier invoices, checks them against purchase orders and queues payments. The vendor claims "a 94% success rate." The starter repo has the vendor's team (as given), 15 invoice scenarios and a spec. Build the evaluation harness the spec describes, re-measure success, cost per task and p95 latency yourself, and pass the provided tests. Make the one call the spec leaves open (what counts as success when the team queues a payment for the right amount but the wrong supplier account), and decide whether you'd recommend buying.     Warm up first: before you measure anything, you'd ask the vendor questions. For each vendor answer below, decide: fine, needs a follow-up, or walk away.

    Warm-up: which answer is a red flag?

    What to submit

    • TRANSCRIPT.md: three judged transcripts, with your own pass or fail next to the judge's

    Integration Concept Debate — connecting all 4 HOS

    Discussion board · 3 stages
    This week's question

    Which is the bigger production risk: a single agent with too many tools, or a team of agents with no evaluation?

    You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

    Side A — Too many toolsGroup 1 this debate

    A single agent with too many tools is the bigger risk.

    • Wrong-tool errors grow with every tool added (HOS 2, and HOS 3's s5).
    • One instruction can't describe twenty tools well.
    • Staff-only tools end up reachable by customers.

    Side B — No evaluationGroup 2 this debate

    A team of agents with no evaluation is the bigger risk.

    • Nobody knows whether the team is better, or just slower and pricier.
    • Routing mistakes are invisible without scenarios.
    • Confident wrong answers ship without a judge or a human check.
