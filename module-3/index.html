What's the HOS?

HOS 3 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 5, then Analyze and Understand & Refine in Week 6. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 6. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

Harbor Supply Co.'s customer-support agent passes a quick demo. Run six scenarios and it crashes on an order number with a "#", tells a customer a refund went through that never happened, loops on a shipment check, reports a confident wrong monthly total, and quotes the store's wholesale cost as the price. Three of those five never crash. They just finish politely, wrong.

Week 5 records every run as a trace, with a recorder you build from ADK callbacks, and builds a failure log from the traces alone, without reading the source code. Week 6 opens the code, fixes each root cause by hand, and adds generic guards that let the agent recover from failures nobody planted.

Anchoring analogy

Debugging an agent from its trace is like an airline incident review from the flight recorder. You can't ask the pilot what they were thinking. You have the instrument readings, second by second, and you reconstruct the decision that went wrong. On-call debugging of agents works the same way: an exported trace, no access to the code, and a customer waiting.

Learning objectives

By the end of the two weeks you will be able to:

  1. Read a reasoning trace step by step: model input, decision, tool call, result, reply. CO3
  2. Classify agent failures: tool-call errors, logic loops, invented actions, wrong data, wrong tool. CO3
  3. Find the first step where a failure shows up, before reading the source. CO3
  4. Fix root causes, and add generic self-correction: errors as observations, repeat-call detection, step budgets. CO3
  5. Explain why a confident wrong answer is harder to catch than a crash. CO3

Lecture: reading traces and making agents correct themselves

≈ 60 min3 short partsCO3

Three short segments instead of one long one: read the notes, then try the quick check before moving on. If something stays fuzzy, that's exactly what your Muddiest Point is for.

Part 1 — What a reasoning trace shows ≈ 20 min

A reasoning trace is the step-by-step record of one run: every model input and output, every tool call with its arguments and result, and the time and tokens for each. ADK records a run as events, and adk web shows them two ways: the Events tab lists them, and the Trace view shows each model call and tool call as a timed span. The recorder you build this week writes the same steps to a file, so you can compare runs and keep them as evidence:

[ 0.9s] CALL   list_orders({})
[ 1.0s] RESULT list_orders -> {"orders": [ ...5 orders... ]}
[ 2.3s] SAYS   "We received 5 orders in September, totaling $1,622.79."

Read a trace the way you'd check a colleague's work: what did the model know at each step, what did it decide, and does the next step follow from the last result? Each claim in the final reply should trace back to a tool result. If you can't find where a number came from, that's a finding.

⚠ Common mistakes

  • Reading only the final reply. The reply sounds right in every scenario. The evidence is in the steps.
  • Treating "no red" as "correct". A run with no errors can still be wrong.
  • A recorder that changes the run. Callbacks that only record must return None. If before_tool_callback returns a dict, ADK skips the real tool and uses the dict as its result.

Going further (optional): ADK can export its traces over OpenTelemetry to hosted tools such as Langfuse or Google Cloud Trace, which keep traces from many users. Nothing in this HOS needs them.

Quick check

Nothing in that trace is an error. What would you check to know whether the answer is right?

Part 2 — Five ways agents fail ≈ 20 min

Failure typeWhat it looks like in a trace
Tool-call errorAn exception on a tool call, often bad arguments ("#1004" into an int).
Invented actionThe model calls a tool that doesn't exist, or says it did something no tool did.
Logic loopThe same call with the same arguments, again and again, getting no closer to done.
Wrong dataA tool returned incomplete or misleading data, and the model trusted it: a confident wrong answer.
Wrong toolA vaguely described tool matched the request better than the right one.

The rule for this HOS: diagnose from the trace first. Write your failure log (scenario, failure type, first step where it shows, symptom, likely root cause) before you open tools.py. Guessing from code is easy; production doesn't give you the code.

Worked example

Scenario s1: "Where is order #1004?" Step 2 calls get_order(order_id="#1004"); step 3 is a ValueError and the run ends. Failure type: tool-call error. First step: 2, where the argument still has the "#". Likely cause: the tool expects an int and nothing cleans the input. Real models vary: on another run the model may strip the "#" itself. Run each scenario twice and log what reproduced.

Quick check

Of the five failure types, which ones can produce a run with no error anywhere in its trace?

Part 3 — Self-correction: fix causes, then add guards ≈ 20 min

Fixing each planted bug makes this agent correct. Guards make the next agent resilient to bugs nobody planted. Both guards are ADK callbacks:

def error_as_observation(tool, args, tool_context, error):   # on_tool_error_callback
    return {"status": "error", "error": f"{tool.name} failed: {error}",
            "hint": "Check your arguments and try once more, or explain the problem."}

def repeat_call_guard(tool, args, tool_context):               # before_tool_callback
    # same tool + same args more than twice this run -> skip the call, tell the model to stop

Add the step budget you already know from HOS 1 (max_llm_calls). Two more ADK tools for self-correction: a reflection loop, where a LoopAgent has a reviewer check the last answer and repeats until it passes or hits max_iterations (it catches some wrong-data failures, at the cost of extra model calls), and tool confirmation, where a risky tool such as a refund pauses until a person approves it.

⚠ Common mistakes

  • A guard instead of a fix. Guards catch what you didn't plant; they don't excuse the bugs you found. Fix the cause first.
  • Comparing arguments too strictly. 1002 and "1002" are the same request. Decide how your repeat guard compares them, and say why.
  • Retrying actions that move money. Recovering from a failed read is safe; retrying a refund may refund twice.
Quick check

Which of the five planted failures would the two guards fix on their own, without the root-cause fix? Which would they miss?

▶ Rehearse before the build: Open the Trace Detective Simulator. Diagnose five traces without code, then switch the guards on and watch which failures recover, and which don't.

New words this week (5)
Reasoning trace
The step-by-step record of a run: each model input and output, each tool call and result, with timing and tokens.
Logic loop
The agent repeats the same action (or a short cycle) without getting closer to done.
Confident wrong answer
A run that finishes politely and is wrong, with no error anywhere.
Guard (callback)
Code that runs around every tool call to turn failures into something the model can recover from.
Reflection
A step where the agent reviews its own last result and decides whether to accept it or retry.

    Concept Debate

    Discussion board · 3 stages
    This week's question

    When a tool fails, is it safer for the agent to crash loudly or to recover and keep going?

    You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

    How your side is assigned

    Before the first debate you join Debate Group 1 or Debate Group 2, either assigned by your instructor or chosen yourself, as long as the two groups stay close to even. You stay in that group all term; find yours under Communication → Groups. The sides rotate each HOS, so nobody argues the same kind of position all term:

    HOS 1HOS 2HOS 3HOS 4Integration (Wk 8)
    Group 1Side ASide BSide ASide BSide A
    Group 2Side BSide ASide BSide ASide B

    Not in a group? (for example, you added the course late) Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A.

    Side A — Recover and keep goingGroup 1 this HOS

    Turn errors into observations; let the model fix its input or explain the problem.

    • Customers get an answer instead of an error page.
    • Most tool errors are fixable input mistakes ("#1004").
    • Guards make recovery generic, not per-bug.

    Side B — Crash loudlyGroup 2 this HOS

    Stop the run and surface the error to engineers.

    • A crash is visible; a recovered-but-wrong answer isn't.
    • Recovery can hide bugs that should be fixed at the source.
    • For actions that move money, stopping is safer than improvising.
    AI use

    You may use an AI assistant to test your thinking, for example by asking it for the best objection to your side. Your posts must be your own words and your own reasoning: don't paste or lightly edit AI text. If AI changed your thinking, say how in one line. AI Use Guide →

    Trace recorder spec (write your own prompt from this):
- support_agent/tracing.py records every run with ADK callbacks
  (before/after model, before/after tool): one line per model call
  and per tool call, with time since start, the tool's arguments
  and result, and the tokens each model call used.
- run_scenarios.py saves each scenario's trace to traces/<id>.txt
