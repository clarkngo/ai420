HOS 3: Traces & Self-Correction

Harbor Supply Co.'s customer-support agent looks fine and fails in several different ways. Find every failure from the traces alone, before you read its source code — the way on-call engineers debug agents they didn't write. Then make it correct itself.

Est. 3–4 hrsOutcome 3Module 3 · Weeks 5–610% of final grade

Before you start

  1. Check your setup. No new accounts this module: your GitHub account, Antigravity and your Gemini key are enough. If adk web hasn't run on your computer since HOS 2, run through your first run again before Week 5.
  2. Know the concepts. Read Concept Companion → Module 3 before you open the starter code.

What you'll need

  • Starter code: your HOS 3 repo, created when you accept the HOS 3 invite. Clone it, open the folder in Antigravity, make the .venv and run pip install -r requirements.txt (or open it in a Codespace, where that happens for you). Not sure what a file does? See the starter code walkthrough for this HOS.
  • Your free Gemini API key (no credit card) from aistudio.google.com/apikey. In the HOS folder: cp .env.example .env, then paste it in as GOOGLE_API_KEY.
  • Google Antigravity, the free desktop app, for Stage 1 (install guide). In a Codespace, use Copilot instead.

Reference reading (optional, before you start)

  • Google ADK documentation: read the pages on callbacks (the before/after hooks you'll use in Stages 1 and 4) and on loop agents (how a loop is supposed to end, with exit_loop or max_iterations).

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your Module 3 GitHub Classroom repo: written work under the matching heading in NOTES.md, screenshots in screenshots/. Commit and push as you go, then submit the repo link to the HOS 3 assignment in Brightspace by the end of Week 6.

🛠️

1 · Create / Scaffold

Graded as Engagement: 20% of this HOS. The AI-assisted starting point, not the deliverable.

Don't open support_agent/tools.py or agent.py yet. First run the six scenarios and read what comes out:

python run_scenarios.py

Each scenario prints only its final reply, and every reply sounds reasonable. To see what the agent actually did, you need a trace. Open one scenario in the dev UI first:

adk web

Pick support_agent, type the s1 request ("Where is order #1004?"), then open the Trace view: each model call and each tool call is a timed span. That's ADK's own trace. Now you'll build a recorder that writes the same steps to a file for every scenario, so you can compare runs. This time you write the prompt for Antigravity yourself, from this spec:

Add support_agent/tracing.py, which records a run with ADK callbacks (before_model_callback, after_model_callback, before_tool_callback, after_tool_callback): one line per model call and per tool call, with seconds since the run started, each tool's arguments and result (or error), and the tokens each model call used. run_scenarios.py already imports support_agent.tracing if it exists; it should save each scenario's trace to traces/<id>.txt and print it. Recording turns on only when TRACE=1 is set. The callbacks only record and always return None. Don't open or change tools.py, or what agent.py does.

Use /plan and read Antigravity's plan before you approve it. Check one thing in particular: does it attach the callbacks to the agent without changing its instruction or tools? Then run the scenarios with recording on:

TRACE=1 python run_scenarios.py

On Windows PowerShell, run $env:TRACE=1 first, then python run_scenarios.py. Keep your prompt; you'll submit it.

Submit (Engagement)
  • The prompt you wrote from the spec and a two-line summary of Antigravity's plan, under Create in NOTES.md.
  • Screenshots of one file in traces/ and of the same scenario in adk web's Trace view.

2 · Evaluate

The critical gate — find every failure from the traces, not the code.

For each scenario, decide from the trace alone: did it succeed? If not, fill in one row of a failure log:

ScenarioFailure typeFirst step where it showsSymptomLikely root cause
s1-…tool-call error / logic loop / invented action / wrong data / wrong tool / nonee.g. step 2, the first check_shipment resultWhat you actually seeYour best guess, before reading the code

Not every failure crashes. Watch for runs that finish politely and are still wrong. For any number the agent states, check it against what the tools actually returned. Run each scenario twice: the model isn't deterministic, so note which failures reproduce. For one failing scenario, also compare your file with the Trace view in adk web: if your recorder missed a step, fix the recorder before you trust the log.

Submit
  • A screenshot of one failing run in adk web's Trace view.
  • Your failure log, one row per scenario, written before you opened the source.
🔬

3 · Analyze

Why does this happen, mechanically?

Now open the source. Pick the one failure you think is most dangerous in production and explain it fully:

  • Which line of code or instruction causes it, and why does the model behave the way it does given what it was told?
  • Why didn't it crash, or, if it did, why is crashing actually the less dangerous outcome here?
  • How would a real customer or manager find out, and how long might that take?
Submit
  • A short written walkthrough of the one failure you chose, in your own words.
✋

4 · Understand & Refine

The mastery check — by hand, no AI assistance for this stage.

By hand this time — no AI assistance for this stage.

Fix each root cause you found in tools.py and the instruction. Then add two generic guards that don't know about any specific bug, in support_agent/guards.py, attached as ADK callbacks:

  • on_tool_error_callback: when a tool raises, return an error dict the model can read instead of crashing the run.
  • before_tool_callback: count identical calls (same tool, same arguments) within one run. After two, skip the real call and tell the model the result won't change. (Hint: returning a dict skips the tool; returning None lets it run. Keys starting with temp: in tool_context.state last for one run only.)

Attach both with the agent's callback arguments, alongside your recorder. Rerun all six scenarios with TRACE=1. Keep the --max-calls budget in place (it sets RunConfig(max_llm_calls=...)): it's the last line of defense if a model ignores your guard.

Optional, if you have time: try one of ADK's heavier self-correction tools on the failure your guards still miss, and say what it cost in model calls:

  • A reflection loop: a LoopAgent with your agent and a short reviewer agent that checks the answer against the tool results and calls exit_loop when it passes, with max_iterations=2.
  • Tool confirmation: add a real issue_refund tool that asks a person to approve it before it runs. Check the current ADK docs for how your version requests confirmation.
Submit
  • Your guards.py and a short list of the fixes you made to tools.py and the instruction.
  • Before/after traces for two scenarios, showing the agent now recovering on its own.
🧯

Common snags

  • A scenario ends with LlmCallsLimitExceededError — that's the step budget from --max-calls stopping a runaway loop. It's a finding, not a problem with the script.
  • A trace looks different each run — expected; the model isn't deterministic. If a failure doesn't show up, run that scenario again with --only. Base your log on what you saw, and note when behavior varied.
  • traces/ stays empty — recording is off. Check that TRACE=1 is set in the same terminal (on PowerShell, $env:TRACE=1), and that the callbacks are attached to the agent run_scenarios.py actually runs.
  • The scenarios behave differently with recording on — one of your callbacks returns something. A recorder must return None; a dict from before_tool_callback replaces the tool's result.
  • Token counts are all zero or missing — they're on the model response (its usage metadata), so read them in after_model_callback, not before.
  • Huge red tracebacks in the terminal — ADK logs every tool error. run_scenarios.py quiets that logger and records the error in the trace instead. If Antigravity rewrote the script, check it kept that line.
  • 429 RESOURCE_EXHAUSTED — you hit the free tier's per-minute limit. Wait a minute and rerun; the scripts' --pause option adds a gap between runs.
  • In a Codespace only: adk web opens a blank page, and the terminal shows 403 Forbidden for /dev-ui/...js files — ADK blocks requests that arrive through Codespaces' forwarded URL. Stop it and start it as adk web --allow_origins "*", then hard-refresh the tab. That's safe here: Codespace ports are private to your GitHub account by default.
  • 502 Bad Gateway, a 404 or "model not found" — almost always the model name. Coding agents, Antigravity included, default to whatever model was current in their training data, such as gemini-2.5-flash, which new API keys can't use. Set it back to gemini-3.8-flash. If that ever stops working, check the current list at ai.google.dev/gemini-api/docs/models.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 3.
